# 早间检查与收口（08:30）

夜跑应当在 07:45 前归档退出。你的任务是**核实并收口**，让用户 09:00 开始工作时拿到一个干净的树。**自己在 09:00 前结束**，不要占用日间开发。

不做新任务。发现的问题只记录、不动手。

## 步骤

1. 读昨晚的报告：`D:\WorkSpace\_night\runs\` 里最新的一份 `*-night.md`（文件名日期即那晚的标记，早检产物用同一个日期）。
   - 如果报告显示 `NIGHT-SUMMARY` 缺失或流程半途而废 → 说明夜跑异常退出，收口要格外仔细。
   - **如果压根没有夜跑报告**（比如机器整夜关机、夜跑被跳过）→ 说明白"昨夜没跑"，照常做其余步骤，别编造昨晚的结果。
   - **如果报告开头写着「编排器兜底报告」**→ 这是夜跑没走完归档、编排器替它留的痕：昨夜是**失败**（断网 / 无头 CLI 起不来 / 被强杀，原因在 `*-night.log` 末尾），不是"机器没开"。照样收口，摘要里写清失败原因和"今晚要不要照常跑"。
2. 检查 `_night\.lock`：
   - 还在，且运行器没在启动时强杀成功 → 说明夜跑进程可能残留。核实后 `taskkill /PID <pid> /T /F`，并把情况写进报告。
3. **逐个检查动过的项目**（报告里有记录；没记录就自己 `git status` 扫一遍活跃项目）：
   - 有未提交改动 → 提交一条 `夜跑收尾：<项目> · <说明>`。
   - `LOG.md` / `README.md` frontmatter 有没有漏更新 → 补上（补的时候标一句「早检补记」）。
   - 提交前若 `git` 报 `.git\index.lock` 占用（多半是夜里断电 / 强杀留下的）：确认没有别的 git 进程在跑（早检时段无人），锁文件年龄**超过 10 分钟才删掉**再提交。这是"不删文件"边界里的**唯一例外**；拿不准就跳过这个项目、记进摘要。
4. **清单收口**：
   - `[未完成]`：留在原位、补/核准「下一步：…」（下一晚夜跑会优先接着收尾）。
   - **不要**因为"看着难、积压多、时间不够"改 `[搁置]`——搁置只用于"需要用户拍板 / 依赖外部条件"的事，并在摘要里点名。没轮到的 `[待跑]` 原样留着，积压顺延是正常状态。
5. **预生成前日简报**（目标是"09:00 弹窗时什么都不用现算"）：
   - 运行 `node D:\WorkSpace\_night\brief.mjs --build`（默认总结"昨天"，正是刚过去这一晚的日期）；生成物在 `_night\brief\`，同时会刷新看板。
   - **能写就顺手写 3–5 句人话摘要**：照 `D:\WorkSpace\_night\prompts\brief-notes.md` 的格式，把摘要写到
     `D:\WorkSpace\_night\brief\notes-<前日日期>.md`（例如 `notes-2026-10-15.md`）。写不出来就跳过——简报照出，只是少一段人话。
   - **不要自己弹审核窗口**：09:00 的计划任务 `WorkSpace-DailyBrief` 会把「前日总结 + 两级清单的 [待审]」合成**一个**窗口弹出（用户勾选＝同意，自动变 `[待跑]`；关窗/超时＝什么都没批）。你再弹一个就是两个窗口，用户会烦。
6. 写早间摘要 `_night\runs\<同一日期>-morning.md`：
   - 昨晚完成了几条 / 未完成几条 / 各自结果一句话
   - 需要用户决定什么：`[待审]` 明细（09:00 的窗口会把它摆到用户面前，这里列明细是为了留档）
   - 今早工作树是否干净、前日简报是否已预生成（写没写人话摘要各说一句）
7. 运行 `node D:\WorkSpace\ws.mjs tree` 刷新项目树。
8. **最后回复用 3–5 句话向用户汇报**（这条会被用户直接看到）：昨晚做了什么、还剩什么、要他点头什么。

## 边界

- 不 `git push`、不改 remote、不 `git reset --hard`、不删文件。
- 不修改夜间机制自身（`_night\` 下除 `runs\` 外的文件）。
- 只收口，不开新工。
